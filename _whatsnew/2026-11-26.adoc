=== Well-architected dashboard enhancements
Workload Factory now includes the following enhancements to the well-architected dashboard.

link:https://docs.netapp.com/us-en/workload-fsx-ontap/configuration-analysis.html[Learn more about best practice recommendations for your FSx for ONTAP file systems.]

=== New recommendations for SAP HANA workloads in the well-architected analysis
Workload Factory now includes the following SAP HANA configurations in the well-architected analysis for FSx for ONTAP file systems:

* *Ransomware protection for SAP HANA*: recommends disabling NetApp Autonomous Ransomware Protection with AI (ARP/AI) on SAP HANA data and log volumes and protecting them with SnapCenter tamperproof snapshots.
* *Single Availability Zone deployment*: recommends placing SAP HANA data and log volumes on a Single-AZ file system.
* *Dedicated storage VM for SAP HANA*: recommends using a storage VM dedicated to SAP HANA.
* *Separate storage VMs for data and log volumes*: recommends serving SAP HANA data and log volumes from separate storage VMs.
* *Dedicated volumes*: recommends separate SAP HANA data, log, and shared volumes.
* *Volume style*: recommends FlexVol volumes for SAP HANA data, log, and shared volumes.
* *NFS TCP max transfer size*: recommends setting the NFS TCP max transfer size to 262144 on storage VMs that serve SAP HANA.
* *Subnet placement*: recommends deploying the EC2 instance that runs SAP HANA in the same subnet as the file system that holds the SAP HANA volumes.
* *Application-consistent snapshots*: recommends protecting SAP HANA data volumes with SnapCenter plug-in for SAP HANA or SAP HANA data snapshots.
* *Cold data tiering*: recommends the "None" tiering policy for SAP HANA data, log, and shared volumes so active database data stays on high-performance storage.

=== New recommendations for Kubernetes workloads in the well-architected analysis
Workload Factory now includes the following Kubernetes configurations in the well-architected analysis for FSx for ONTAP file systems:

* *Snapshot expiration*: recommends deleting the VolumeSnapshot in Kubernetes so Kubernetes and the storage stay in sync.
* *Inactive NAS volumes* and *Inactive block devices*: recommends archiving the data to the capacity pool tier or removing the persistent volumes in Kubernetes.
* *Use Trident for Kubernetes persistent volumes*: recommends provisioning Kubernetes persistent volumes with NetApp Trident so Kubernetes manages the full volume lifecycle.
* *Trident provisioning model*: recommends using Trident NAS Economy provisioning for large-scale Kubernetes environments.
* *Volume count*: recommends reducing the number of volumes on a file system before it reaches its volume limit so Kubernetes can create new persistent volumes after the limit is reached.
* *Volume capacity headroom*: for volumes that back Kubernetes persistent volumes, recommends expanding the persistent volume claim or using a Trident _Autogrow Policy_ instead of resizing the volume. The 80% threshold is unchanged.

=== New recommendations for storage VM name services
*DNS and LDAP server redundancy*: recommends at least two DNS servers on storage VMs that use DNS, and at least two LDAP servers on storage VMs that use LDAP. A single server failure can block name resolution, domain authentication, or NFS access.

=== Volumes explorer enhancements

==== New Volumes explorer table columns
The Volumes explorer table includes the following new columns:

* *Logical used size*: shows the space that clients see as used, before storage efficiency savings. This column appears by default.
* *Junction path*: shows the junction path for a volume.

==== Manage mount points
You can now manage where volumes are mounted in a storage VM namespace directly from Volumes explorer. Select *Manage mount points* from the *Advanced* menu for a volume to view the storage VM namespace as a tree, then mount, unmount, or change the mount point (junction path) for the volume. Workload Factory checks dependencies before it unmounts a volume. You can't unmount a volume that has other volumes mounted under it, and you get a warning when the volume has SMB shares. 

=== Nested junction paths for new volumes
When you create a volume, you can now enter a nested junction path, such as `/test1/test2`, in the *Advanced configuration* section. 

link:https://docs.netapp.com/us-en/workload-fsx-ontap/create-volume.html[Learn how to create a volume]

=== File system inventory enhancements

==== Bulk SSD and throughput management
You can now manage Performance tier (SSD) capacity and throughput capacity for one or more file systems at a time from the file system inventory. Select the file systems, then choose an action from the new *Elasticity* section in the actions menu. For each action, choose a mode: none, recommendation (notify only), or automate. You can also adjust the thresholds for each action. For SSD capacity, choose either incremental or adaptive mode. Workload Factory automatically selects credentials with the required permissions for each file system and logs each operation in Tracker.

==== New inventory columns
The file system inventory includes new columns for SSD used capacity, SSD usage, P95 and P99 throughput, average and maximum throughput, HA pairs, and deployment type. 

=== Associate multiple file systems with a link
You can now associate multiple FSx for ONTAP file systems with a new or existing link in one workflow from the Link management page. You can enter different ONTAP credentials for each file system, or apply the same credentials to several file systems. 

link:https://docs.netapp.com/us-en/workload-fsx-ontap/links-overview.html[Learn more about links]

=== Improved snapshot capacity estimates in savings calculators
All savings calculators use the same snapshot capacity calculation. The calculation adds snapshot capacity to the capacity pool tier and uses the used capacity when it's available, or the provisioned capacity otherwise. The shared calculation gives you more accurate FSx for ONTAP sizing and savings estimates.
